# NEOFORM audit — 19 October 2026

Read-only product/code review. No application behavior, access mode, personal accounts, programs or workout history was changed. Findings are a backlog for later work, not fixes already delivered.

## Assessment

NEOFORM is a credible personal workout logger with a promising mini-coach foundation. Its strongest qualities are the compact mobile logger, explicit load conventions, portable exports, cautious training language, account isolation and unusually substantial regression tests. Keep these.

The largest weaknesses are correctness at the edges of offline sync and coaching, and a storage design that does not support a lifetime of history comfortably. It is not yet an adaptive personal coach: AI constructs a starting program from bounded preferences; the deterministic coach uses a small recent-history window and conservative rules. That is a useful foundation, provided the product describes it accurately.

My recommendation is to keep Cloudflare and fix correctness and persistence before adding more AI or rebuilding the UI.

## Confirmed bugs and data-quality problems

Priority P1 means fix before expanding coaching/public use; P2 means fix in the next reliability pass. Line references describe the audited checkout.

### B01 — P1: an obsolete offline journal can undo a newer synced edit

**Code:** `src/store.ts:165`, `:224`, `:330`.

Each page instance gets a new tab ID. Dirty snapshots are written to that tab's pending journal. After a reload, the new tab reconciles the old journal, but a successful acknowledgement removes only the new tab's own journal. The abandoned journal remains eligible for reconciliation.

**Browser reproduction:** make a theme change while PUT requests are blocked; reload; restore connectivity and sync; change the theme back and sync successfully; trigger another sync. The old theme reappears and is saved to D1. This demonstrates stale edit replay with a harmless setting. Similar journal semantics apply to training state; workout deletion/resurrection was not separately tested.

**Fix direction:** retire or acknowledge incorporated journal generations using durable provenance. Never discard an independently unacknowledged tab's work. Add reload → acknowledgement → subsequent edit/delete → resync regression tests, including two live tabs.

### B02 — P1: moving an exercise can save the editor without explicit acceptance

**Code:** `src/App.tsx:2015`–`:2042`, inside `ProgramBuilder`.

Native reorder buttons inside the form omit `type="button"`. Their default submit behavior invokes the program save handler.

**Browser reproduction:** open a program, click its first “Move exercise down” button. The dialog closes and the reordered program persists without clicking “Save mesocycle”. A separate initial suspicion about removing a target was not reproduced and is not reported as confirmed.

**Fix direction:** explicitly type non-submit buttons throughout forms. Verify that reorder/remove/add operations remain in the preview until Save and are discarded on cancel.

### B03 — P1: editing a program can silently activate another program

**Code:** `src/App.tsx:503`; active-program selection in `src/WorkoutHome.tsx:36`.

Saving removes the edited program and appends it. Active identity is inferred from the first unarchived program in array order.

**Browser reproduction:** create two unarchived programs, edit/save the first, and the second becomes active.

**Fix direction:** update the existing array position; ultimately store an explicit active-program ID with backward-compatible migration. Editing should never be an activation operation.

### B04 — P1: skipped prescribed sets become unknowable, allowing misleading progression

**Code:** `src/domain.ts:400`–`:415`, `:899`, `:1314`–`:1390`.

The historical target stores rep range, RIR and rest, but not planned set count. Completing a session deletes unfinished sets. The coach compares completed-set counts between exposures, so two equally incomplete workouts can look like a completed, repeatable dose.

**Domain reproduction:** prescribe three sets, complete only one at the rep ceiling, repeat that partial workout, supply favorable recovery. The coach recommends a load increase.

**Fix direction:** snapshot planned dose separately from actual completed work, including skipped-set status/reason. Incomplete adherence should require review, not become evidence that the full prescription was achieved. Preserve legacy records as unknown.

### B05 — P1: phase context leaks into progression

**Code:** `src/domain.ts:1279`–`:1322`; `src/CompactLogger.tsx:146`.

The comparison key does not contain phase, and progression-history selection does not filter session phase. The current program phase only vetoes escalation when that current phase is recovery-oriented.

**Domain reproduction:** two maintenance-phase sessions at RIR 3 qualify for a load increase when the current phase is accumulation. Maintenance recipes can prescribe RIR 3, which passes the existing `<5` effort filter.

**Fix direction:** compare against the current draft's snapshotted phase and execution context. Define explicit rules for re-establishing baseline after maintenance/deload or a changed prescription; do not silently mix them.

### B06 — P1: deload arithmetic treats machine labels as physical loads

**Code:** `src/domain.ts:793`–`:828`.

Late deload workouts halve the previous numeric load regardless of convention.

**Domain reproduction:** a leg-press label of 7 becomes 3.5. A numbered pin/label is not a measured load ratio or necessarily an available setting. This conflicts with the app's otherwise careful handling of machine labels.

**Fix direction:** keep machine/band label changes manual and explicit. Real load changes also need available-increment checks. Do not infer a percentage reduction from arbitrary labels.

### B07 — P2: “one more rep” can reduce the first two sets

**Code:** `src/domain.ts:1440`–`:1453`; `src/CompactLogger.tsx:485`–`:495`.

The recommendation uses the lowest latest-set rep count plus one, then acceptance applies that single value to every unlogged working set.

**Domain reproduction:** two repeatable 12/10/8 exposures produce a target of 9; acceptance produces 9/9/9. That is fewer total reps than 12/10/8, not a per-set rep increase.

**Fix direction:** offer row-specific targets or an explicit total-rep objective while preserving the intended effort and comparable set order.

### B08 — P1 for coach evidence: target RIR is also the default actual observation

**Code:** `src/domain.ts:832`–`:865`, `:890`; `src/CompactLogger.tsx:220`–`:240`.

New sets prefill actual reps and RIR from targets. Completion alone marks those numbers as completed observations; there is no observed/confirmed flag. Numeric RIR is mandatory in the schema.

**Domain reproduction:** checking a new untouched set records eight reps, RIR 2 and load 0. Defaults are convenient, but the engine cannot distinguish accepted defaults from reported effort.

**Fix direction:** separate target values from actual values and distinguish confirmed effort from unknown/unconfirmed effort. Preserve fast logging; a subtle per-set confirmation or short finish check can avoid crowding the main logger. Never use unconfirmed RIR as strong coaching evidence.

### B09 — P2: the next workout is guessed from total session count

**Code:** `src/WorkoutHome.tsx:38`–`:39`; `src/domain.ts` session schema lacks `workoutId`; dashboard shortcut in `src/App.tsx:1058`–`:1073` always uses workout zero.

**Browser reproduction:** complete workout B before A in a three-workout program; home recommends B again because one completed session means index one. Skips, repeats, deletions and out-of-order sessions can all desynchronize this rule. The dashboard and Workout tab also use different next-workout rules.

**Fix direction:** snapshot workout identity and track explicit sequence/schedule state. Offer “repeat”, “skip”, “reschedule” and “choose another” without silently rewriting history. Use one shared next-workout selector.

## Hosting: keep Cloudflare, improve how NEOFORM uses it

There is no defensible guarantee of free, unchanged service for an individual's lifetime. Under the currently published allowances, Workers + D1 is a strong fit for this application's small personal workload. I would not migrate it just to seek another free tier. This is an architecture recommendation, not confirmation that the existing account is on a free billing plan.

| Option | Fit for this app |
| --- | --- |
| Existing Cloudflare Workers + D1 | Best default: already integrated, minimal operating work and good free allowances. Optimize before moving. |
| Vercel Hobby with a database provider | No clear gain for this Worker/D1 app; requires backend changes and another data service. Hobby is limited to personal/noncommercial use. |
| Supabase Free | Useful when managed auth/Postgres becomes necessary. A migration is substantial and inactive free projects pause after one week. |
| Static offline-only PWA | Could remove the server dependency for solo logging, but loses automatic cloud/multi-device persistence unless another sync mechanism is added. Browser storage still needs backups. |

Current published Cloudflare limits: Workers Free allows 100,000 dynamic requests/day and 10 ms CPU per invocation. Direct static-asset requests are free and unlimited. D1 Free provides 5 million rows read/day, 100,000 rows written/day and 5 GB total storage, with a 500 MB maximum per database. Free D1 Time Travel covers seven days. See [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) and [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).

Specific improvements:

1. **Route static assets directly.** Production currently sets `run_worker_first: true` in `scripts/cloud-launch-policy.mjs`. Every shell/asset request invokes the Worker. Use selective API routing and static `_headers` to retain CSP/security headers. Cloudflare explicitly warns that Worker-first assets can return 429 when free Worker request limits are exhausted: [asset billing/routing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/).
2. **Replace full snapshots on every poll with revision checks.** `src/store.ts:619` polls every 15 seconds, including hidden tabs. Each clean sync downloads and validates all history and persists it again. A continuously active tab could make 5,760 polls/day, before edits/assets. Real usage is lower when tabs close or browsers throttle timers; this is arithmetic, not measured production usage. Pause hidden-tab polling, add backoff, elect one tab where practical, and return lightweight unchanged/revision responses.
3. **Remove the one-row lifetime-history ceiling.** Account data is one JSON row, capped at just under 2 MB by `stateSchema`. This is far smaller than the database allowance, and the error currently tells the user to remove old sessions. Store sessions separately, paginate/archive without deletion, and use bounded transactional updates with tested migration/rollback.
4. **Use IndexedDB for durable local data.** The outbox stores current data plus a common base, and copies that into both shared cache and pending journals. This multiplies localStorage usage and synchronous work. Old journals also accumulate. Request persistent storage where supported, expose backup status, and retain export/recovery paths.
5. **Add private operational diagnostics.** Observability is disabled. Capture sanitized error categories, request/CPU/DB usage and release identity without bodies, keys or workout records. Verify worst-case account validation and authenticated routes against the free CPU limit; local test success does not prove that boundary.
6. **Test restore, not just export.** Add an owner-controlled backup/restore procedure and periodic restore drills. Seven-day recovery is not a lifetime backup. Keep encryption-master recovery separate from ordinary training JSON backups.

Free hosting does not imply free AI. Optional Gemini usage has separate provider quotas/costs, and the currently public workspace disables it. Retain useful deterministic coaching even when a provider is unavailable. No live provider-cost or model availability claim is made by this audit.

Alternative references: [Vercel Hobby restrictions](https://vercel.com/docs/plans/hobby), [Supabase pricing and inactivity policy](https://supabase.com/pricing).

## Algorithms that need strengthening

- **Progression:** fix B04–B08 first. Replace one scalar rep target with per-set or total-rep decisions, add equipment increments, current prescription/context matching and explicit uncertainty. The 2.5%/2.5 kg cap is a disclosed conservative policy, not a personalized optimum. Do not remove it without replacement tests.
- **Recovery:** seven-day feedback and 21-day performance windows are coarse software choices. Add a short pre-session check and repeated response review; distinguish illness/travel/sleep/context from training-dose problems. Keep missing data unknown, keep pain separate, and never infer measured growth or volume landmarks.
- **Program generation:** the provider sees preferences and a filtered catalog, not training history, actual weekdays or personal response. The validator enforces schemas/equipment/set budgets but coverage, priority, complementary actions, spacing and detailed time feasibility are primarily warnings. Define explicit eligibility/quality gates, preserve valid goal-driven omissions, and evaluate plans against synthetic scenarios before claiming individualization.
- **Scheduling:** store actual workout IDs and intended weekdays; support missed-session recovery and rest days. AI “Day 1/Day 2” labels do not establish sensible spacing.
- **Insights:** the review hardcodes an 8–12 range (`src/App.tsx:2580`) instead of selecting the relevant exercise prescription. Exercises programmed at 5–8 or 12–20 can get unhelpful holds. Derive context explicitly or let the user choose it. Preserve the honest raw-bout timeline label rather than presenting mixed methods as strength progress.
- **Training decisions:** the saved choice contains only key, choice and time, not an immutable recommendation/evidence snapshot. Store policy version, input references, suggested change, accepted change and later outcome to make reviews auditable.

| Order | Feature | Acceptance condition |
| --- | --- | --- |
| 1 | Reliable next-session card | Correct workout identity, last comparable performance, row-specific proposal and visible reasons; accept/edit/decline. |
| 2 | Pre-session readiness and movement tolerance | Brief optional check; unresolved pain and missing data handled safely; no diagnoses. |
| 3 | Equipment/setup profiles | Available dumbbell/plate increments, machine identity, seat/attachment/ROM notes; no fictitious load equivalence. |
| 4 | Planned-versus-completed review | Preserve skipped sets and reasons; weekly adherence and muscle exposure with uncertainty. |
| 5 | Missed-session and short-session options | Explicit preview of redistributed work/rest days; no forced catch-up volume. |
| 6 | Weekly/mesocycle review | Summarize repeatable performance, recovery and adherence; retain productive exercises; approve future edits. |
| 7 | Backup/recovery and private account access | Storage meter, restore rehearsal, offline status, and a considered account-recovery/passkey option if private hosting is used. |
| 8 | Better logger ergonomics | Undo recent actions, duplicate/repeat a session with context, optional screen wake lock, clearer timer limitations. |
| 9 | Optional long-term measurements | Bodyweight/measurements/photos only if wanted; private/exportable and never presented as proof that a particular workout caused growth. |
| 10 | Catalog and custom-exercise coverage | More demonstrations and editable secondary involvement for custom exercises; explicitly label involvement estimates. |

Keep the approved mobile layout. Put explanations and advanced planning in sheets or finish/review flows; do not add a dense coaching dashboard to the primary logger.

## Engineering and release backlog

- Split the roughly 3,500-line `App.tsx` into feature modules and separate large policy/schema/catalog concerns in `domain.ts`. Lazy-load import/AI/insight tools; preserve behavior and visual baselines.
- CI currently typechecks, runs the main tests, builds and checks the AI boundary, but does not run the real Worker/D1 API or browser suites. Add isolated integration gates and the regressions above before deployment.
- Make local test setup portable: default scratch space from the OS or a QA directory instead of assuming CI-only variables; parameterize API test ports and browser executable paths. The Windows first-run failure is reproducible, even though supplying `TMPDIR` makes the suite pass.
- Retire or clearly quarantine historical sidecar/provisioning/probe scripts. The current architecture is simple; leftover experimental paths make maintenance and audits harder.
- Update contradictory documentation: README still describes hosting as a future handoff and `.wrangler/state` as local persistence; SECURITY and README disagree about historical provider qualification. Replace stale run-specific prose with current architecture plus dated evidence.
- Reassess password hashing before broad private-account use. The code uses PBKDF2-SHA512 at 100,000 iterations; current [OWASP guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) lists 220,000. This is disclosed already. Evaluate runtime-compatible stronger authentication with safe hash migration; do not blindly increase work in a 10 ms free-runtime budget. No existing password records were inspected.
- Review abuse controls for the intentionally anonymous shared workspace. Same-origin checks prevent browser cross-site writes but do not authenticate command-line clients. Decide whether anonymous editing is still the intended product; preserve the current flag until explicitly changed.

Suggested implementation sequence: sync journal correctness → explicit program saves/activation → coaching evidence and phase/label fixes → regression/API/browser CI gates → durable lifetime storage and efficient hosting → scheduling and mini-coach features. No runtime implementation or deployment was performed as part of this review.
