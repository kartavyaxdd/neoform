# Security and limits

Server-derived session identity scopes every data query. The client's `X-Neoform-Account` header is an expected-identity guard, never authority: a mismatch with the shared browser cookie returns 412 before reading or changing data. D1 statements bind parameters. Seven-day opaque 256-bit session cookies are HttpOnly, SameSite=Strict and Secure on HTTPS. Only token SHA-256 digests are stored. Logout revokes the current session; password change revokes other sessions. Login's final session insert checks that the verified password hash/salt still match, fencing concurrent password rotation. Deletion cascades through sessions and account data. Mutation requests require an exact same-origin Origin header, including sign-up/login. CSP, no-sniff, referrer, permissions, HTTPS HSTS and private-response no-store headers apply.

Passwords: WebCrypto PBKDF2-HMAC-SHA512, 100,000 iterations, distinct random 128-bit salts, 256-bit result, minimum 12 characters, maximum 128. This uses the native WebCrypto API and stays within the reported Workers 100,000 iteration ceiling. That work factor is below current OWASP SHA-512 guidance (220,000, checked 2026-10-09); use long unique passphrases. Native Argon2 or a stronger compatible KDF should be reassessed when platform support changes. Do not misrepresent this as OWASP work-factor compliance. The real local Worker API tests execute the KDF. Parent must review this limitation and verify free-plan CPU quotas and deployed-runtime behavior before public release.

References: [Cloudflare WebCrypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/), [Workers PBKDF2 ceiling issue](https://github.com/cloudflare/workerd/issues/1346), [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Rate limiting: atomic D1 counters, 10 attempts per normalized email and 100 per IP per 15-minute window, sensitive authenticated actions also capped. Expired counters/sessions are pruned during successful sign-in. Generic login errors; no credentials or bodies logged. Registration may indicate that account creation failed. No email service/reset is claimed. No telemetry SDKs. Optional owner-supplied Gemini API usage may incur Google charges; no billing/account settings are changed by the app.

Full account snapshots have strict schemas, bounded arrays/numbers/text and a 2 MB request/backup limit, with space reserved for request/export wrappers. Updates use atomic revision compare-and-swap. Offline changes are account keyed; generation and account-epoch fences prevent delayed acknowledgements from erasing edits or restoring a logged-out account. Safe three-way sync merge preserves independent edits/deletions and refuses competing changes. Export backups before choosing replacement. Local data is removed on logout/account deletion. Offline logout records a signed-out marker so an unreachable surviving cookie cannot automatically restore the account; it cannot revoke that cookie on the server until online. An offline draft cached on your own device is not encrypted at rest: use trusted devices and OS protections. Service worker caches only the public static shell, never API/auth responses. No security-bypass auth paths.

## Gemini account keys and bounded model requests

- Only the authenticated server-derived account can read key status (`configured` only), replace or remove its key. All mutations require same-origin and the expected-account guard; keys are never returned, included in backups, or cached in browser storage. Period-containing header-safe keys are preserved literally.
- AES-GCM uses a fresh 96-bit nonce and AAD `neoform-gemini-v1:<account-id>`. Ciphertext lives in account-scoped D1; a stable 256-bit master is held in ignored server-only `.dev.vars` locally or a server secret in hosted deployments. Keep that master private and backed up. Replacing it without a migration makes existing ciphertext unreadable; setup refuses to overwrite an existing invalid master.
- Gemini runs directly through the authenticated Worker using the fixed configured model and a stateless (`store:false`) structured-output interaction. No agent, tools, function execution, shell, CLI, alternate provider/model or preset fallback is available to customer requests. Request preferences are strict enums/numbers, not arbitrary prompts. Only public compatible catalog entries and bounded preferences are sent.
- Provider output is independently validated against the full strict program schema, canonical exercise IDs, equipment, movement limitations, repetitions and set-volume bounds. The provider schema uses Google's documented supported subset; full string-length checks still apply after generation. Preview is editable and requires explicit acceptance before saving.
- Auth cleanup explicitly preserves the day-window `gemini-global-day` row; signing in/registering cannot reset the allowance. A real isolated QA red/green regression verifies this mixed-window-unit boundary.
- Durable D1 counters cap attempts per account (3/15 minutes) and globally (10/day by default); the global lease allows concurrency 1. Incoming disconnect, explicit account-scoped cancellation and a 110-second timeout abort upstream work. No key/request body is logged and upstream errors are not forwarded verbatim.
- The real QA key lifecycle, account isolation, ciphertext storage, browser field clearing and explicit-save behavior are tested. **A successful genuine Gemini generation is not yet established**: current live attempts encountered overload/invalid-argument responses or timeout. Model metadata alone is not successful generation evidence. Historical subscription and synthetic fixture proof must not be presented as current Gemini success.

Application data imports are untrusted. JSON format is strict and versioned; CSV cells are quoted and leading formula characters neutralized. React escapes text. There are no HTML injection sinks. Owners should retain private backups and review Cloudflare access controls. Automated tests verify important boundaries but do not replace independent security review or live-runtime validation.

## Workspace profiles

The existing hosted installation explicitly enables `WORKSPACE_PROFILES` alongside its workspace flag. Sharma keeps the existing `public-workspace` storage owner; Abhishek has a distinct `profile:abhishek` owner and starts empty. No private-account tables or original workout rows are copied or replaced. An additive migration creates profile metadata and separate session credentials. Profile names and whether they are locked are public; workouts require the selected profile's server-issued HttpOnly/SameSite cookie. Abhishek is intentionally open until a lock is requested.

Locked profiles use the existing salted PBKDF2-SHA512 parameters and one-time operator provisioning over stdin; no password appears in source, backups or API responses. Unlock requests require same origin and are limited to 12 attempts/profile and 40/IP per 15 minutes. Short user-selected locks provide convenience, not strong protection against guessing. Ordinary account password requirements are unchanged. The server derives storage ownership from the cookie and rejects mismatched expected-owner headers; no client-supplied profile ID can select another owner's storage. Legacy whole-workspace data routes are closed in profile mode, as are private-account administration and provider keys.

Lock/switch waits for pending sync, revokes the current cookie, hides state across tabs using existing account fences, and clears only this profile's synced device cache while preserving pending journals. Unlocked offline data remains unencrypted on the device under the existing offline policy. This cannot revoke copies previously obtained while the workspace was public. Existing notification installation credentials remain separate from workout backups.
